# Story 31 — 주제별 출처 그룹 쌍 독립성 승인

기준: `prototype` 병합 헤드 `477fb64`. Story 30은 실제 기사 호스트와 설정 source의 그룹 승인 이력을 수집 스냅샷에 고정했다. 서로 다른 그룹 ID만으로 독립성을 인정하지 않는다. 사용자 결정에 따라 자동 발행은 검증 가능한 정형 글에만 재개할 예정이며, 이 스토리에서도 v3 생성 글은 계속 `HELD`다.

## 범위

- 관리자가 같은 주제에 속한 서로 다른 두 출처 그룹에 대해 편집상 독립성 승인을 명시적으로 기록한다. `(낮은 그룹 ID, 높은 그룹 ID)`로 순서를 정규화하며 근거, 승인·취소 시각, 활성 상태, revision, 취소 근거와 감사 이력을 보존한다. 자기 자신·다른 주제의 그룹 쌍은 거부한다.
- 관리자 전용 목록·생성·revision 기반 취소 API와 UI를 제공한다. 현재 및 과거 승인을 모두 볼 수 있고, 중복 활성 승인과 오래된 revision은 409로 응답한다. worker/public 응답에 편집상 승인 근거를 추가하지 않는다.
- 새 실행을 생성하는 짧은 트랜잭션에서 주제 행을 잠그고 그 시점의 활성 그룹 쌍 승인을 `automation_run_origin_pair`에 ID·revision·정규화된 그룹 ID로 불변 복사한다. 승인·취소도 같은 주제 행 잠금을 사용한다. 중복 idempotency key로 기존 실행을 재사용하면 캡처를 갱신하지 않고, 보류 실행의 재시도는 별도 새 실행에서 현재 정책을 캡처한다. 수집·외부 네트워크 호출은 이 트랜잭션 밖에서 유지한다.
- Flyway V16은 이력 보존형 승인 테이블과 실행별 캡처 테이블을 추가하고 유일성·FK 제약을 둔다. run detail에는 캡처된 쌍의 ID·revision·그룹을 관리자에게 표시한다. 승인 취소·새 승인 뒤 과거 실행의 캡처는 바뀌지 않는다.
- 명시적 쌍 승인은 정책 증거일 뿐 사실 확인이나 숨은 재배포 독립성의 증명이 아니다. 향후 양성 발행 게이트는 캡처된 source-host 승인과 쌍 승인이 모두 현재도 활성·같은 revision인지 재확인하고, 같은 호스트·설정 source·공유 상위 보고서 veto를 적용해야 한다. Story 31은 자동 발행을 허용하지 않는다.

## 수용 기준

1. 관리자만 같은 주제의 서로 다른 그룹 쌍을 승인·조회·취소할 수 있고, 근거·revision·감사가 남는다. 순서를 뒤집은 동일 쌍, 동시 중복 승인, 오래된 revision 취소는 결정적으로 충돌한다.
2. 실행이 시작된 뒤 새 승인·취소를 해도 그 실행의 고정 증거는 변하지 않는다. 중복 실행 재사용은 원래 캡처를 유지하고, 새 재시도 실행은 새 시점 정책을 캡처한다.
3. 빈 MySQL Flyway/Hibernate validation, 승인·취소·실행 경합, 관리자 인증·감사, UI 상호작용, worker/public 계약 미변경, 기존 v3 `HELD` 판정과 전체 게이트를 검증한다.
4. 한국어 이슈→검증→커밋→PR→CI→`prototype` 병합 순서를 따른다. 독립 verifier, 코드 리뷰, 적대적 QA의 미해결 중요 지적이 없어야 한다.

## 운영 경계

자동 승인 추론은 하지 않는다. 그룹 쌍 승인 목록이 많아질 때 실행 시작의 읽기 비용과 캡처 수가 증가하므로 해당 수를 계측·제한하기 전 무인 발행 판단에 사용하지 않는다. 출처 근거 보존 기간과 선택적 조회 경로도 무인 운영 전 과제다.
