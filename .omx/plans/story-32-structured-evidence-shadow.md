# Story 32 — 정형 출처 관찰 계약과 음성 검증

기준: `prototype` 병합 헤드 `b0b3300`. 사용자는 검증 가능한 정형 글만 자동 발행하도록 선택했다. v3 자유 서술은 인용 ID만 제출하므로 Spring이 문장별 진위를 검증할 수 없다. 이 스토리는 양성 발행을 열기 전에, 출처에 실제로 나타난 **문구의 존재**만 다루는 좁은 v4 계약과 Spring 검증·렌더링 기반을 만든다. 문구의 존재는 그 문구가 주장하는 사실의 진실을 뜻하지 않는다.

## 범위와 안전 경계

- v4 성공 제출은 기존 자유 서술 `draft`와 구분되는 `observations` + `taxonomy` variant다. worker가 제목·요약·Markdown·HTML을 공급할 수 없고, 최대 3개의 `SOURCE_MENTION` 관찰을 공급한다. 관찰마다 공백 정규화된 20~160자 문구와 정확히 2개의 서로 다른 같은 실행 snapshot ID를 요구한다. 실패 제출은 기존 terminal 계약을 유지하고 v2/v3는 그대로 처리한다.
- v4 작업도 v3와 동일하게 enqueue 시 taxonomy catalog를 고정하고 claim에 전달한다. Spring은 제출된 taxonomy ID를 고정 catalog와 현재 행에 대조한다. worker는 v4 claim만 처리 가능한 지원 버전 목록을 선언해야 하며 v2/v3 active 작업과 혼합 배포해도 각 버전의 계약을 지킨다.
- Spring은 각 스냅샷이 같은 실행에서 수집됐고, `ALLOWED`이며, 보존된 기사 증거가 존재하고 잘리지 않았고, 저장된 증거 해시와 일치하는지 검사한다. 해시는 Story 29가 저장한 원문 텍스트 바이트로 먼저 재계산한다. 이후 문구 매칭에 한해서 문구와 증거를 Unicode NFC로 정규화하고 Unicode 공백 연속을 ASCII 한 칸으로 접으며 대소문자는 보존한다. 앞뒤 문자가 문자·숫자가 아닌 완전한 연속 부분 문자열만 일치한다. 단순 부분 단어, 빈 값, 마크업·제어문자, 다른 실행의 ID, 동일 ID 두 번, 해시 불일치, 절단, 중복·모호한 관찰은 거부한다. 이 검증은 ‘두 출처에 같은 문구가 나타남’만 판정하며 독립성이나 사실의 진위를 판정하지 않는다.
- Spring은 이번 단계에서 정형 제목·본문을 렌더링하거나 게시물 초안으로 저장하지 않는다. v4 원본 관찰은 접근 제한된 작업 결과 JSON에만 보관하고, 검증 결과·이유·snapshot ID와 문구 해시만 관리자 진단에 보관한다. 문구나 기사 원문은 관리자/worker/public 응답에 추가 노출하지 않는다. 추후 공개 템플릿은 두 출처에서 해당 문구가 관찰됐다는 귀속만 표현해야 하며, 문구가 사실이라고 단정할 수 없다.
- v4 검증 결과가 양성이어도 이번 스토리의 모든 v4 실행은 `HELD`다. v3의 `CLAIM_EVIDENCE_UNVERIFIED` 보류와 수동 override 정책을 유지한다. v4에서 수동 override는 별도 승인 설계 전까지 허용하지 않는다. v4는 게시 경로를 호출하지 않으며, 양성 발행에서 필요한 원자적 중복 게이트는 후속 스토리 범위다.
- v4는 publication service의 별도 shadow 경로로 처리하고 자유 서술 draft 저장·관리자 파싱·수동 override 경로로 떨어지지 않게 한다. 동일 terminal ID·digest 재전송은 검증 전에 기존 응답을 그대로 반환한다. v4 실패 제출은 기존 실패 경로를 사용한다.
- 구조적으로 유효한 관찰의 증거 부족·불일치는 terminal 제출을 수락한 뒤 음성 진단과 함께 `HELD`로 남긴다. 알 수 없는 JSON 필드, 잘못된 타입·개수 등 계약 위반은 상태 변경 없이 400으로 거부하고, digest·lease·서로 다른 terminal 재전송 충돌은 기존 409 의미를 따른다.
- 버전별 producer/consumer, JSON schemas, canonical digest, fixture, provider 대체 테스트를 함께 수정한다. v4로 전환하는 기본값은 바꾸지 않는다. 기존 배포의 active v3 작업은 계속 v3로 처리한다.

## 수용 기준

1. v4 스키마와 worker가 자유 서술 필드를 거부하고, 실패 제출·idempotent 재전송·lease 검증은 기존과 동일하게 동작한다. v2/v3 직렬화와 계약 테스트는 유지한다.
2. 빈 MySQL에서 Spring은 저장된 기사 증거만 사용해 동일 문구의 존재를 결정적으로 검사한다. 타 실행·정책 차단·증거 없음·잘림·해시 변조·부분 단어·중복·모호한 입력을 음성 fixture로 검증한다. 재수집이나 외부 네트워크 호출은 제출 트랜잭션에서 하지 않는다.
3. 양성 검증도 `HELD`로 끝나며 게시물·revision·outbox가 생기지 않는다. v3는 기존 보류 사유를 유지한다. 관리자 진단에서 문구 원문이 노출되지 않는다.
4. 백엔드 check, 프런트엔드·worker lint/typecheck/test/build, Playwright, Compose, 독립 verifier·코드 리뷰·적대적 QA와 PR 필수 검사가 깨끗하다. 한국어 이슈→커밋→PR→`prototype` 병합 순서를 따른다.

## 후속 양성 발행 게이트

Story 33에서 캡처된 source-host 승인과 그룹 쌍 승인이 현재도 같은 revision으로 활성인지 확인하고, 같은 source/host 및 명시적 `SHARED_UPSTREAM`을 veto한다. MySQL 원자적 중복 보호와 출처 귀속 템플릿의 안전한 렌더링·게시·outbox를 한 트랜잭션으로 묶고 난 뒤에만 `SOURCE_MENTION`의 양성 자동 발행을 허용한다. 자유 서술의 사실 주장 자동 발행은 별도 검증 가능 문법 없이 열지 않는다.
